## 1. 结论

原计划提出的“提高提炼质量、减少重复概念、增强证据一致性”是合理目标，但多项代码前提与当前实现不符。报告缺少对具体页面的失败样例、评估样本及合格标准，因此无法据此判定整个工程“不合格”，也无法直接推导出必须全面重构。

适合采用的方向是：围绕实际质量缺口建立可复现评测，再试点抽取中间对象、概念对齐和候选检索。当前的证据归档、提案、版本检查、自动发布和主题导航可继续作为基础。

## 3. 实施前应修正的设计

### 3.1 抽取阶段与表达编辑阶段各有职责

原计划把“概念 / 断言抽取 + 页面综合”与“草稿 + 润色”混用。前者产生可复用知识中间对象，后者只改善已有正文表达。

建议试点流程：

```mermaid
flowchart LR
    Source[归档原文与版本] --> Extract[抽取概念、断言、范围和摘录]
    Extract --> IR[可缓存的抽取中间对象]
    IR --> Match[检索并对齐已有概念]
    Match --> Plan[目标页面与待处理问题清单]
    Plan --> Write[按目标生成页面提案]
    Write --> Validate[结构、摘录、版本及语义疑点检查]
    Validate --> Publish[复用现有发布与主题导航机制]
```

中间对象与待处理清单是建议新增能力，尚未实现。当前一次请求已经输出断言与正文，但这些断言不会先作为独立抽取结果缓存，再用于多个目标页面。

试点期间保留现有单遍流程作为对照。是否增加调用应由质量收益、失败率、延迟和成本决定。额外表达编辑不能顺手增补知识、实验结论或未经证据支持的例子。

### 3.2 验证摘录存在与验证语义支持

验证应分为三个层次：

1. **确定性检查：** 来源存在、版本一致、摘录匹配、引用合法、旧 ID 未遗漏。复用当前程序约束。
2. **语义检查：** 断言是否扩大原文范围、改变确定程度、遗漏实验条件、错配比较对象。可由独立 Agent / 模型提出判断，但必须保存理由、证据及版本，允许“部分支持 / 无法核查”。
3. **研究有效性：** 实验是否可靠、结果是否复现。不能由引文存在或模型核查自动保证。

“程序检查摘录包含断言文本”不是可靠验收方法：中文归纳与英文原文可能语义一致但没有共同字句；包含相同关键词也可能条件不同。

### 3.3 旧知识保护不能靠盲目补回数组

把旧 `claims` 直接并入新稿，可能产生“元数据保留、正文遗漏”的假完整性。当前已有 ID 保护，不宜用自动补回隐藏模型遗漏。

需要评测两类真实缺口：同一 ID 被改写成不同含义，以及正文包含未登记为 Claim 的旧事实。可增设结构化变更说明，区分新增支持、措辞调整、范围修正、被新证据挑战等情况；旧判断及依据继续留在历史中。

已有 `_require_quoted_changes()` 的新增 / 改动摘录要求由自动发布策略强制。不同发布入口的约束是否应统一，需要明确策略并做专门回归，不能宣称已经“所有入口、所有历史断言都强制齐备摘录”。

### 3.4 相似度用于候选，不能直接批准合并

标题相近可能是同义表达，也可能是机制与具体实现、通用概念与实验设置的区别。固定向量阈值或 Jaccard 阈值只宜提供候选。

合并方案还需处理：规范 slug、别名、旧链接重定向、断言 ID 冲突、适用范围差异、来源及关系迁移、核查记录过期和恢复。自动实体唯一映射是目标假设，不能当作已经证明可行的规则。初版宜先做同义命名提示和路由建议，验证后再实现页面迁移。

报告的聚类伪码省略了 embedding 模型、距离度量、连接方式、阈值校准和误合并评测，不能直接作为生产配置。

### 3.5 保持现有存储和发布职责清晰

- 正式知识元数据当前以 `wiki_meta/*.json` 为主要结构化存储。YAML frontmatter 可以是导出格式；若引入第二份可编辑副本，需要明确权威数据与同步规则。
- 当前系统检查后自动发布，疑点保留为待处理记录。原计划的强制人工审批属于产品流程变更，需要单独决定，不能混进证据校验修复。
- `--topic` 当前表示知识问题，不表示页面类型。新增类型选择应使用独立参数及契约。
- Source 的 `approved` 表示已参与发布，不表示原文所有知识已经提炼。多目标流程应另记覆盖情况及未完成目标，避免借现有 stage 表达新的完成语义。

## 4. 建议实施顺序与验收

下列顺序按依赖和风险安排。工期、模型及调用预算需在试点后估算，不沿用原报告的固定“1～2 周 / GPT-4”假设。

| 阶段 | 可实施范围 | 验收依据 |
| --- | --- | --- |
| **P0：建立质量基线** | 固定公开资料与知识问题样本；覆盖同义概念、不同机制、范围冲突、长文节选、旧知识更新；记录现有真实候选路径。 | 每个失败有原文、预期目标、当前输出和原因；可分别衡量召回、路由、断言支持及正文保留。 |
| **P0：厘清校验契约** | 区分阻断性错误、语义待核查和表达建议；核对不同发布入口策略；补充同 ID 语义变化、正文遗漏的失败样本。 | 没有把提示当事实认证；结构变更和疑点可追溯；现有发布回归继续通过。 |
| **P1：抽取与编写试点** | 在新流程中缓存抽取中间对象；以来源版本、提取方式、schema 和提示版本作为缓存身份；按概念目标生成提案。 | 同一抽取可支持不同问题；失败目标可重试；来源变更使缓存失效；比较单遍与分阶段的质量、成本和延迟。 |
| **P1：概念对齐与覆盖清单** | 先增加别名和召回建议；记录每个来源的已处理 / 待处理知识问题；保留主题导航职责。 | 应合并的同义表达能路由到已有页；不同机制保留区别；发布一页不丢失其他待处理目标。 |
| **P2：检索升级** | 从真实候选路径抽出统一接口；先比较当前规则、别名扩展与全文排序，再决定 FTS5 / BM25 / embedding。 | 固定数据集的 Recall@k、正确目标排名、误匹配、中文召回、索引更新与检索延迟有对照结果。 |
| **按需：原文处理** | 根据扫描 PDF 和图表依赖样本决定 OCR、页码、结构化表格或视觉读取范围。 | 原件与抽取版本可追踪；字符位置 / 页码区分明确；不会把部分读取表述为全文理解。 |
| **按需：发布恢复** | 建立持久发布日志、恢复状态与巡检命令，设计写入中断的恢复步骤。 | 注入进程中断后可识别未完成发布；恢复幂等；正式正文、元数据、主题导航及状态能协调恢复。 |

“断言准确率 90%+”需先定义分母、样本选择、判断规则及标注者一致性。建议将断言支持精度、知识问题覆盖率、误合并率与旧知识保留分开统计；不能用一个百分比代替所有质量问题。

每个试点保留输入版本、原文片段、候选及路由、模型 / 提示版本、失败原因和输出差异。固定公开评估集无需含用户私密资料。

## 6. 外部参考核验

本节仅核对报告提及的主要一手来源及适用边界，不声称完成全文复现或全部参考文献审计。

- **Karpathy：** [原始 LLM Wiki gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 明确是设计模式说明，不是现成官方栈。它提出持久 Wiki、原始来源及 schema，也明确实现选项可按需求选择。“Karpathy-LLM-Wiki-Stack 官方示例仓库”的归属不能由该 gist 证明；需要原报告补充精确链接。
- **AtomicStrata：** [llm-wiki-compiler 官方仓库](https://github.com/atomicstrata/llm-wiki-compiler) README 确实介绍两阶段提取 / 页面生成和混合检索。它支持将这些机制作为参考；不能据此证明本工程采用同样机制必然改善，也不能单凭 README 确定成熟度。
- **Ming 等：** [Retrieval as Reasoning: Self-Evolving Agent-Native Retrieval via LLM-Wiki](https://arxiv.org/abs/2605.25480) 确实存在，摘要介绍 Wiki 编译、工具调用和 Error Book，并报告指定问答数据集结果。它是另一项研究工作；摘要成绩不能直接外推为本项目的论文提炼质量保证。
- **GraphRAG：** [官方索引流程](https://microsoft.github.io/graphrag/index/overview/) 介绍实体、关系、断言抽取、社区检测、摘要及向量化。可参考其阶段分工，不要求本项目立即引入图数据库或整套索引流水线。

原报告其余模糊命名来源和英文“原文”示例尚未逐字核验；后续引用应补充准确 URL、版本与段落位置，不能仅凭示例文字当作已验证论文摘录。
