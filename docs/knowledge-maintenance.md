# 知识维护：决策、综合与一致发布

本轮实现将知识维护与正文写作拆成独立任务，复用既有 SQLite、L2 提炼、正文绑定和发布恢复机制。工程回归、模型决策合理性、知识正确性与最终发布状态分别验收。参考决策集仍待人工审阅；首轮真实模型发现的问题与本轮修复及复验见[修复复验记录](knowledge-maintenance-revalidation.md)，历史实现边界见[首轮工程交付](knowledge-maintenance-delivery.md)。本文不固定测试计数。

## 四层职责与执行路径

| 层 | 职责 | 持久化对象 |
| --- | --- | --- |
| L1 原始资料 | 归档与可定位解析 | 原件、来源版本、页码与段落 |
| L2 知识提炼 | 理解单篇研究 | 已接受解读、知识点、结果、claim 与证据 |
| L3 组织与演化 | 维护决策、综合、独立审核、发布 | 多对多归属、暂缓状态、概念页、关系与变化历史 |
| L4 知识服务 | 阅读、导航、检索与问答 | 页面呈现、主题入口与可恢复索引 |

生产编译入口 `compile_job` 在论文处理后默认调用 `synthesize_library`。首次建库与增量维护共用同一决策逻辑；已有有效 L2 知识无需为了 L3 改动重新提炼。维护流程可直接读取已接受的当前知识点；L2 内容或来源版本实际变化时才需要处理对应提炼结果。

L3 顺序为：收集待处理点与候选概念 → 维护决策 → 契约及版本校验 → 写作 → 独立绑定 → 事实与知识变化审核 → 分组发布。`wiki_experiment.run_trial` 调用相同综合核心，并设置 `publish_pages=False`，只保存草稿和检查结果。显式发布实验是另一个操作，会重新验证固定输入、Skill 与概念版本。

## 决策、缓存与修正

- `knowledge-maintenance/v1` 为独立维护契约，每个待处理点恰有一条 `linked` 或 `deferred` 结果；一个点可有多个概念归属，各自保存角色与理由。归属使用 `core`（必须解释的核心认识与条件）、`supplementary`（按需选择的例证和边界）、`related`（概念关联/导航）三种作用。默认必要表达集合只含核心点；同一点在不同概念中可有不同作用。旧 required/background 归属分别兼容为 core/related，旧页已有核心义务保留。
- 无匹配候选不等于证据不足：维护必须比较新点之间能否形成稳定解释问题。`deferred` 必须给出具体知识或证据障碍及 `reevaluate_when` 重评条件；不能为覆盖率强制建页。
- 概念动作有 `create`、`update`、`no_change`。高风险合并、拆分、撤回、替换及无法确认的知识失效进入待审，不作为普通更新自动执行。`unresolved`、审阅要求与校验问题可阻断发布。
- 新点、内容或来源版本变化、Skill/模型身份变化进入待处理；暂缓点还会在候选概念变化或相关新点出现时重评。候选依靠已有归属与文本相关性召回，目标缓存依据相关点、来源、概念版本与执行身份，避免无关材料新增导致整库正文重写。
- 决策和写作保留解释、范围、可迁移性、不确定性、结果及 claim 关联。原文以去重证据库和位置引用传递；读者页面在相关论述自然表达必要条件，不展示内部字段清单。输入超过显式上下文预算时阻断，不静默删除知识点。
- 作者按已校验决策组织解释，不重新规划归属。正文之后统一运行绑定；纯格式或定位问题修复绑定，保持正文不变。事实遗漏、条件丢失或含义错误才进入正文修正。事实审核与知识点/合并变化审核分别执行。
- 关系缺失ID由程序按来源概念、目标、类型、事实/编辑依据稳定生成，已有ID保持；绑定允许不连续段落，精确字符/字节范围由程序提取。标题外壳和应用路由在绑定前规范化，原始响应留存。发布边界再次核对所有引用位置。
- L3采用 `knowledge-review/v2`：问题区分事实错误、遗漏、错误合并、关系、契约和表达建议，阻断需明确位置及可追溯依据。表达建议不阻断；未展开可选知识不强制补写，已写出的任何事实仍须独立原文支持。旧正文直接交给审核，不能仅靠旧断言ID是否存在判断知识保留。审核或元数据契约错误不会作为正文语义错误重写整页，未能校验的稿件保持未发布。
- 维护请求、作者、绑定与审核使用持久化请求预算；默认初次请求加至多两轮修正。请求前预占预算，重启或续跑不能刷新耗尽次数；工作区冲突不算一次模型尝试。失败记录和未发布草稿保留。
- 旧 `alignment-*` 缓存保留作历史审计，不作为新维护契约的有效决策直接复用；新的决策和目标缓存有自己的协议与身份校验。

## 发布、来源失效与检索

同一工作区使用独占 L3 运行锁。发布前在发布锁内重新检查来源、点内容、概念正文/元数据及归属版本；新建概念必须仍不存在。来源重新提炼时，消失或变化的旧点保留变化历史，并将相关归属标为 `pending_review`，不会静默删除已发布解释。

共享知识点或关系依赖的概念按同组发布；组内页面先共同进入导航规划，可引用同批新页。共享主题和首页使用组内累积结果，避免后写页面覆盖先写链接。同组正文、元数据、归属、关系与维护执行状态，通过既有文件发布日志与数据库事务提交；异常按发布日志恢复。暂缓与无变化只持久化对应状态，不为此重写页面。

搜索索引是可恢复的派生数据。发布事务设置 `index_dirty`，索引随后独立重建；编译任务会调用现有索引步骤。词法重建在发布锁下读取一致快照，仅无读取警告时清除脏标记。向量索引仍有独立后端身份及就绪检查，词法更新不表示向量已完成。索引失败后保留已提交知识及恢复标记，不把过期索引标为就绪。

## 在离线副本验证

优先运行仓库离线测试及 [参考集结构测试](knowledge-maintenance-reference.md#可复验检查)。需要使用真实论文数据时，先在工作区之外准备包含数据库与文件的**一致离线副本**；不要直接拷贝正在写入的 SQLite 文件或将示例路径指向活动库。下面展示已有 Python API，使用显式 Workspace 和本地响应回放，不读取活动库注册配置，也不调用远程模型：

```python
import json
from pathlib import Path
from station.workspaces import Workspace, use_workspace
from station.knowledge_synthesis import synthesize_library

# 这些文件由测试准备；副本保留原 library_id 与来源身份。
root = Path('/tmp/llm-wiki-maintenance-review/skill-preview').resolve()
assert root.is_dir() and (root / 'state.db').is_file()
recordings = json.loads((root / 'offline-model-responses.json').read_text())

# 每条回放记录包含完整 messages 与 response；不匹配就停止，绝不回退网络。
def offline_model(messages):
    if not recordings:
        raise AssertionError('Offline responses exhausted')
    record = recordings.pop(0)
    assert record['messages'] == messages, 'Offline request changed'
    return record['response']

ws = Workspace('skill-preview', root)
with use_workspace(ws):
    result = synthesize_library(
        ws, model=offline_model,
        source_ids=['0b44ee6389202cb6', 'eddf2edee3305425',
                    '3fb5d6b0a837235b', 'accd5feccfb2c025'],
        publish_pages=False,
    )
print(result['status'], result['quality_acceptance'])
```

回放响应必须是对应测试场景准备的有效模型响应；参考决策 JSON 是审阅目录，不能直接当成生产响应。该调用会在副本保存决策、预算、缓存与草稿，但不发布页面；默认 API 参数 `publish_pages=True` 适用于生产调用，离线验证必须显式传 `False`。`ready`/`completed` 仅表示自动检查结果，不表示人工接受。
