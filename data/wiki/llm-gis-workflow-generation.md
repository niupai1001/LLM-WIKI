# 自然语言驱动的 GIS 空间分析工作流生成与执行

GIS 工作流把自然语言里的空间条件转换成可执行操作，再把中间数据交给后续步骤。例如设施选址需要结合交通、商业设施和工业区图层；系统必须选对算子、参数和数据，才能得到可检查的候选区域。GeoGPT、GIS Copilot 与 GeoFlow 分别展示了逐步工具调用、宿主软件中的代码生成、显式依赖图这三种组织方式。

## 从需求到可执行步骤

GeoGPT 的作者稿使用 LangChain 与 GIS 工具池。模型在推理、行动与观察之间推进，每次选择工具并读取返回结果，再决定后续操作。设施选址案例先为地铁、超市和工厂数据建立缓冲区，用 `Erase` 排除工厂周边，再用 `Intersect` 找到满足其余条件的区域；输出文件路径把各步连起来。[S:3bdb54f327d29558]

GIS Copilot 运行在 QGIS 中。它先读取数据字段、坐标参考系、范围和分辨率，把任务拆成步骤，再依据 QGIS/GDAL 工具文档生成带参数的 Python 代码。结果回到 QGIS 图层或表格、图表；运行出错时，调试模块读取错误并迭代修正。这里，工具文档既帮助选算子，也帮助填参数。[S:8cabb777c9bc6fe9]

GeoFlow 先生成显式的有向依赖图：节点写清子任务、负责的智能体、函数调用目标与 API，边表示数据依赖。执行按拓扑顺序推进，各子智能体把结果传给下游；出错时，元智能体结合聊天历史与错误信息修改工作流图。把 API 写进目标，是它相对只分解抽象任务的工作流设计所做的具体改进。[S:19f9b059cd25c958]

## 相似机制与不同控制方式

三者都需要工具知识、可传递的中间结果和执行反馈。GeoGPT 的观察来自逐步工具调用，GIS Copilot 把反馈放在代码执行与调试中，GeoFlow 则把依赖关系与修订对象明确表示为工作流图。这是控制方式的比较，各自论文使用的任务与评测协议不同，不能据此排出通用性能名次。[S:3bdb54f327d29558][S:8cabb777c9bc6fe9][S:19f9b059cd25c958]

可以结合[[geospatial-hierarchical-planning-agents|层级规划与容错]]阅读：该页讨论领域依赖和保留有效步骤的恢复方式；本页关注 GIS 工具、代码和中间数据如何组成具体工作流。

## 可验证的范围与限制

GeoGPT 在这里使用的是2023年早期作者稿。其案例展示工具组合的可行性，作者也报告相同设置可能产生不同结果、查询措辞会影响执行，以及工具保护只能缓解部分错误。2024年正式文章是相关后续版本，本页没有据其摘要补入新实验。[S:3bdb54f327d29558]

GIS Copilot 的归档v4评测含110个任务，但正文与Table 1存在报告差异：基础/中级成功率在正文为95%/80%，在表中为92%/83%；高级均为75%。这项内部差异持续保留，不能用任一组数字作为确定结论。参数、字段、数据兼容性和重投影仍可能出错，作者也要求用户检查代码与结果。[S:8cabb777c9bc6fe9]

GeoFlow 在GeoLLM-Engine的20个任务上报告74.2%的平均成功率和64.1%的正确率；工具调用或图生成正确不等于最终空间分析正确。作者指出这些任务多为线性依赖，更复杂的交互式多轮任务仍需验证。可编辑工作流界面属于论文讨论的后续方向，不能当成已完成的普遍能力。[S:19f9b059cd25c958]
