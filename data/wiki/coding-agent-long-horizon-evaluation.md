# 长周期编程评测

长周期编程评测衡量编程助手在持续演进的代码仓库中完成一长串相互依赖的改动，并在多轮对话里反复澄清需求、修正实现的能力。它与单轮修补评测的区别有两点：任务跨越多个文件与模块，后一步依赖前一步留下的代码状态；需求不是一次性给出，而是由用户在多轮交互中逐步透露和修改。SWE-Journey 把这两点放进同一个会话中评测，认为此前工作只覆盖了其中一部分[SWE-Journey](/source/c59a22e9fb289ff4)。

## 工作机制

评测在一个持久的 Docker 容器里进行。助手对工作目录的修改、命令输出和测试结果都累积在同一份代码状态上，而不是提交一个补丁后离线判分；测试在用户认为某阶段完成时和会话结束时各跑一次[SWE-Journey](/source/c59a22e9fb289ff4)。

任务由合成流程构造：先生成高层任务蓝图和子任务，再逐个实现，每个子任务同时生成参考补丁、Fail-to-Pass（F2P，改动前失败、改动后应通过）测试和 Pass-to-Pass（P2P，改动前后都应通过）测试，后者用于检测回归。作者称这种合成方式能降低直接复用公开 issue 带来的答案泄漏风险[SWE-Journey](/source/c59a22e9fb289ff4)。

用户模拟器逐轮提供需求和反馈，并追踪子任务状态。不同用户画像同时改变专业程度、需求表达、控制方式和验证习惯，因此画像是一组协作条件，不只是提示词的语气。[SWE-Journey](/source/c59a22e9fb289ff4)

评测区分新增功能的测试通过率与旧功能的回归情况，也比较阶段完成时和会话结束时的结果。后者与前者的差值反映后续执行的净改善，包含用户反馈等作用，不能独立证明助手自主纠错。[SWE-Journey](/source/c59a22e9fb289ff4)

## 如何使用

适用场景：评估编程助手在真实协作条件下的可靠性，尤其是需求不完整、用户会中途改主意、代码状态持续累积的情况。不适用场景：只关心单次补丁正确性，或希望用固定提示词横向比较模型原始解题能力时，单轮评测更可控。

实践建议（基于证据的推论）：把“用户是谁”当作评测条件的一部分，而不是噪声。同一批任务在不同画像下表现差异很大，报告结果时应说明画像配置，否则数字不可比。

示例（非论文实验）：先要求增加 CSV 导出，下一轮又要求导出沿用现有筛选条件。助手需要在同一代码状态上继续修改，并确认旧报表仍能运行。只检验第一轮补丁，无法衡量这种持续协作。

## 证据与边界

当前依据主要来自 SWE-Journey 的 30 个长周期实例和多模型实验。其结果显示，阶段任务的通过情况与最终结果并不相同，持续编辑仍会引入回归。[SWE-Journey](/source/c59a22e9fb289ff4)

研究将失败分为需求理解、代码定位和实现三个环节。提问与结果的关联提示交互方式值得单独评测，但观察关联并不能证明“多提问”必然带来提升。[SWE-Journey](/source/c59a22e9fb289ff4)

用户模拟器不等于真实用户，合成任务可能继承仓库与模型偏差，公开任务也有答案泄漏风险。因此该基准适合补充单轮评测，不是对真实生产协作的完整复现。[SWE-Journey](/source/c59a22e9fb289ff4)

## 常见误解

第一，把画像差异直接读成“专家知识带来普遍收益”。四类画像在专业程度之外还同时改变了信息透露节奏、控制风格、目标稳定性和验证方式，作者也说明画像结果是完整协作条件的比较，无法分离出单一维度的贡献[SWE-Journey](/source/c59a22e9fb289ff4)。

第二，把用户信心当作正确性。作者明确指出信心不是客观正确性的代理，也没有普遍期望的方向；案例中验证最严格的画像报告了最低信心，却交付了最多的通过测试[SWE-Journey](/source/c59a22e9fb289ff4)。

**任务构建成本等于每次评测费用。** 论文的每实例 56.64 美元用于合成长周期任务，运行助手的 API 费用另行报告。比较评测成本时应分开计算。[SWE-Journey](/source/c59a22e9fb289ff4)
