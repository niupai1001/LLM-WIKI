# LLM Wiki 论文知识提炼

## 目标与边界

本 Skill 处理论文原文，不是摘要改写器。最终回答五个问题：作者要解决什么问题；旧方法为何不够；新设计改变了什么、为什么可能有用；实验证据支持到什么程度；有哪些可迁移知识与领域边界。

单篇论文阅读稿是**来源级解释**，知识点是**可核查命题**，概念页是**跨来源综合**，主题入口是**问题导航**。不能用单篇阅读稿替代概念页，也不能因一篇论文自动建立一个宽泛主题。

本 Skill 的约定产物为 reading.md、knowledge.json、review.md。它们是 Skill 工作产物，**不是当前 LLM-WIKI V2 编译器已支持的直接输入/输出协议**。接入方式见 references/pi-intel-wiki.md；字段约束见 references/artifacts.md。不得擅自将它们写入正式 Wiki 发布目录。

## 何时使用

适用于已取得原文的研究论文、方法论文、Agent 范式讨论、领域 Agent 论文、Benchmark、系统论文和综述。新闻、产品动态及摘要资料应按项目已有流程处理，不强行套用论文工作流。

## 输入要求

读取并保留已有来源标识、来源版本、书目信息、原文与可定位段落/页序、解析状态、可读性缺口、现有 Wiki 候选、旧断言和主题。以调用方真实字段为准；不得编造 source_id、excerpt_id、页码、论文版本或旧 claim ID。

**先检查完整性**：是否取得全文；方法、实验、消融、局限及关键图表是否可读；解析结果是否存在 OCR 或表格缺失。摘要只能用于初筛。若核心结论依赖未读图表，停止相关实证断言并记录待补材料；不将局部阅读冒充完整提炼。

## 执行顺序

### 1. 判定论文贡献类型

可多选：方法机制、Agent 范式/理论、领域应用、数据集/Benchmark、系统工程、综述/观点。确定论文真正的贡献对象；不要将所有论文写成“输入—模块—输出”的相同模板。

### 2. 先重建论证，不急于写正文

在内部形成以下链条：

- 研究目标 → 现有做法 → 瓶颈及后果；
- 核心主张 → 设计选择 A/B → 每个选择解决的具体问题；
- 为什么该设计可能起作用 → 作者是否真的解释；
- 哪项实验检验哪项主张 → 结果支持与未支持的部分；
- 适用范围、失败情形、剩余不确定性；
- 可复用知识与仅在该领域成立的知识。

缺少的因果环节标记为“作者未解释”或“尚无法判断”，不能用常识补写为作者结论。执行细则见 references/reading-framework.md。

### 3. 提取有解释价值的证据

只保留支撑定义、机制、设计理由、代表性结果、消融解释、失败条件和范围限制的原文。区分作者明示、结构直接呈现、提炼者推论、未知。对每个重要命题保留原文位置与版本。原文存在不等于原文支持该命题；核对需覆盖前提、比较对象、限定词与否定词。

### 4. 生成知识候选，而不是零件清单

每个知识点必须能用完整句子表达，至少说清：命题是什么、解决/解释什么、依据何在、在哪些条件下成立、读者为何值得记住。

技术参数只有在影响机制、判断边界或复现关键结论时才进入正文。卷积核尺寸、隐藏维度、接口参数等若只是实现细节，应压缩为功能性说明或留在复现资料中。组件名称不能单独算知识点。

实验部分按“结果 → 支持的解释 → 仍然不能推出什么”组织。主结果证明研究目标是否达成；消融分析机制贡献；失败案例限定适用范围。不要搬运整张排行榜。

### 5. 双重知识身份与领域路由

对每个知识点分别判断：

- **通用机制**：问题、作用对象、输入输出和反馈位置可跨任务复用；
- **领域专用**：成立依赖遥感、GIS、医学等特定数据语义、约束、评测或工具；
- **桥接知识**：机制可迁移，但其有效性或实现条件依赖特定领域。

一篇领域 Agent 论文可以同时贡献三类知识。不可仅因出现“规划、工具、反馈”关键词就合并概念，也不可将遥感实证结果写成所有 Agent 的规律。详细路由见 references/knowledge-hierarchy.md。

### 6. 对齐已有概念与主题

先检查已有概念的问题定义、机制、适用范围和证据，再作 update / create / defer 决策。已有概念可容纳时优先 update；同名但机制不同应区分；证据不足时 defer。主题围绕长期学习问题组织，不等同于采集 category，也不等同于论文标题。

### 7. 写作 reading.md

先用完整自然段说明问题及瓶颈，再解释关键设计和设计理由，最后用少量有代表性的实验分析界定结论。段落之间必须有逻辑承接。尽量使读者不依赖论文的模块命名，也能复述“为什么这样做、怎样发挥作用、证据支持什么”。

单篇 reading.md 的整篇来源归属默认明确，不在每段重复同一论文的 [S:...]。仅在直接引文、重要图表定位、引入其他来源、作者观点与推论易混淆、关键争议需要复核时展示局部出处。**此规则不取消 knowledge.json 的断言级溯源，也不覆盖正式 Wiki 页的引用要求。**

不要把内部概念路由、审核状态或 Schema 字段写进读者正文。写作细则见 references/reading-framework.md 与 references/provenance.md。

### 8. 绑定机器证据

为核心知识点、关键结果和跨来源比较保存可定位的原文证据。原文版本变化必须重新核对绑定；不得凭训练记忆补来源。Skill 的 knowledge.json 结构遵循原有 artifacts.md，不自行增添强制顶层字段。当前仓库 V2 使用 concepts/questions/claims 及 evidence_passages，映射方式见 references/pi-intel-wiki.md。

### 9. 双通道修订

事实通道冻结来源、断言、scope、证据和旧知识保留关系。表达通道可以调整解释顺序、段落、例子和术语，但不得偷偷改变事实通道。表达优化无法消除事实疑点；发现疑点应返回事实核查阶段。

### 10. 独立核查与发布建议

核查者必须重新对照原文，而不只阅读草稿。检查证据支持、数字、限定条件、旧断言保留、领域过度泛化、因果跳跃、段落可读性和概念误合并。产出 review.md，区分 hard block、review warning、editorial suggestion。见 references/review.md。

只有完成当前调用方的 Schema、版本、旧断言和发布检查，才可提交给相应编译/发布接口。本 Skill 不自行宣布已发布或已人工验收。

## 必须阻断的情况

- 没有全文却声称完成完整提炼，或关键结论依赖未读图表；
- 重要知识点没有可定位依据，或摘录不能语义支持断言；
- 推论被写成作者结论，实验局部结果被泛化为通用 Agent 规律；
- 旧断言、冲突、范围或来源被静默删除；
- reading.md 仅有模块清单、参数清单、排行榜或短语拼接；
- 概念归并仅靠名称/关键词，或主题仅靠采集 category 建立；
- 事实核查未通过却尝试绕过当前编译器发布门禁。

## 参考文档的唯一职责

- references/artifacts.md：Skill 产物与字段兼容边界；
- references/reading-framework.md：完整阅读、论证重建、解释性写作；
- references/knowledge-hierarchy.md：知识层级、领域/通用双重路由、概念对齐；
- references/provenance.md：读者引用与机器证据、来源版本；
- references/review.md：独立审核、阻断、质量验收；
- references/pi-intel-wiki.md：当前仓库 V2 接口映射及最小适配。

出现冲突时，以调用方当前真实代码的结构要求为硬约束；Skill 负责提升知识质量，不能通过文档修改声称已经改变程序行为。
