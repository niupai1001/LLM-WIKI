# Reading Framework：从论文原文到可解释的知识

## 职责

负责阅读完整性、论文贡献类型、论证重建和连贯的单篇 reading.md 写作；不定义机器 Schema、发布接口或概念路由。

## 一、阅读前检查

读取标题、版本、摘要、引言、相关工作、方法、实验、消融、局限、结论；根据核心主张检查图表、公式和附录。摘要只能定位问题，不能替代方法与实证。记录 PDF 页序与论文印刷页码的区别；OCR 不完整、图形未读时降低结论范围或阻断。

先判定论文类型：

- 方法：设计选择与因果机制；
- Agent 范式/理论：概念边界、假设和论证，而非硬套工程模块；
- 领域 Agent：领域约束与可迁移机制分别解释；
- Benchmark：测量对象、任务构成、指标是否有效、偏差；
- 系统工程：设计权衡、资源/可靠性条件、可复用实践；
- 综述：分类依据、证据覆盖与争议，不把综述观点冒充实证。

## 二、Argument Reconstruction

写作前在内部填完以下问题，不直接把表格输出成正文：

| 逻辑位置 | 必答问题 |
| --- | --- |
| Goal | 作者究竟想回答什么？ |
| Existing approach | 过去通常如何处理？ |
| Bottleneck | 为什么过去的方法在这里不够？ |
| Consequence | 这个瓶颈造成什么可观察问题？ |
| Central answer | 作者提出什么核心回答？ |
| Choice A/B | 每个设计解决哪个子问题？ |
| Rationale | 作者明确解释了为何有用吗？ |
| Evidence | 哪项实验检验哪个判断？ |
| Limits | 结论依赖什么条件？ |
| Transfer | 哪些认识能脱离具体系统复用？ |

设计理由严格区分：作者明确说明、结构直接可见、提炼者推论、无法判断。后两类不能冒充作者实证结论。

## 三、实现细节过滤器

对每个数字、组件、参数问三个问题：它改变机制吗？它限定适用范围吗？它是读者理解主张所必需的吗？三个答案均为否，正文删除或概括。复现重要但理解非必要的内容放入 source_notes/附录（如果原有产物允许），不要污染知识主线。

不要把“使用 3×3 卷积”“设置某隐藏维度”自动解释为性能提升的原因；除非作者有消融、理论或其他直接依据，否则最多说明组件承担的功能，保留因果未知。

## 四、实验结果转成认识

主结果只说明研究目标是否在所测条件下达成。消融回答“去掉某机制会怎样”；误差分析回答“何时失败”；跨数据集结果回答“迁移证据有多强”。优先写分析结论与限定条件，仅保留最有辨识度的指标、比较对象和必要数字。

反例：连续三段罗列数据集 A、B、C 的每项分数，然后写“证明方法有效”。

改写方向：“在所报告的测试条件下，方法相对比较基线有改善；更重要的是，消融显示去掉 X 后性能变化，因而为 X 的作用提供了有限支持。不过该实验尚不能单独证明 Y 是唯一原因。” 只有原文确有相应结果时才能这样写。

## 五、连贯叙事

每段只承担一个功能，并与前段建立明确关系：提出问题、解释瓶颈、引入解决思路、展开因果过程、检验机制、限定结论、提炼启示。尽量采用“因为……所以选择……；这一选择使……；实验通过……检验……”的逻辑，但不要机械重复句式。

先讲读者能理解的场景，再引入术语；首次出现的缩写解释含义。技术术语必须承担解释功能。举例应区分“论文实验”与“解释性假设场景”。

禁止：模块 A/B/C 的孤立列表；连续无主语短句；用标题和关键词代替因果句；按论文目录逐段翻译；重复同一个结论；以多组分数代替实验分析。

**自检**：遮住论文标题和模块名称，读者是否仍能复述“为什么要做—如何解决—为何可能有效—证据支持什么—适用条件”？若不能，重新组织段落。

## 六、三种 Agent 论文的不同阅读重点

**ReAct**：解释推理与环境行动为何交错；观察如何影响后续决策；不要把它简化为“多一段 Prompt”。实验只能支持论文测试的任务与设置。

**Reflexion**：解释一次尝试的反馈如何变成后续尝试可用的语言反思，反思放在循环什么位置；与 ReAct 的交互反馈有何不同。不要因都有“反馈”就合并机制。

**Change-Agent**：先说明遥感变化检测的具体困难及观测对象，再说明感知输出如何进入 Agent 决策；区分遥感数据结构、空间语义与一般性的工具/反馈编排。卷积尺寸、参数量等只有影响解释或结论边界才保留。若原文未解释某模块为什么有效，必须明确未知，不能凭模型经验补造。

以上是**阅读提问框架**，不是对三篇论文具体实验的事实断言；正式实例必须重新查原文。
